# D 阶段:审计度量(Observability,R6)

> **目标**:agent 行为可审计——执行审计、策略拒绝事件、资源度量——经结构化
> tracing 输出,由 `SandboxPolicy.audit`(AuditSpec)按策略声明驱动。
> 从 R6(可观测审计)推导,非实现遗产。

---

## 1. 设计(从 R6 推导)

**需求**:理解/追责 agent 行为——它执行了什么、被拒绝了什么、用了多少资源。

**审计事件模型**(引擎内结构化事件,经 tracing 输出):

| 事件 | 触发 | 字段 | AuditSpec 门控 |
|---|---|---|---|
| `audit.exec` | sandbox_exec/exec 完成 | sandbox_id, args, exit_code, duration_ms | `audit.exec` |
| `audit.deny` | 沙箱化 exec 被策略拒绝 | sandbox_id, args, reason | `audit.deny` |
| `audit.resource` | 资源相关操作(resize/超限) | sandbox_id, kind, value | `audit.resource` |

**关键语义**:
1. **策略驱动**:审计不是全局开关,而是每策略声明(`policy.audit.deny/exec/resource`)——不同的 agent 信任级别可审计粒度不同(R10 策略可编程的延伸)
2. **结构化输出**:`tracing::info!(audit = "exec", sandbox_id = ..., ...)`——可被日志聚合/告警系统消费,不引入新协议面
3. **拒绝识别**:策略拒绝 = guest sandlock 返回 "denied" 类错误的 exec 失败——engine 在此路径记 deny 事件

## 2. 任务拆分

### T1 — 审计事件 helper(引擎)
- `crates/engine/src/audit.rs`(新):`pub(crate) fn audit_exec(policy: Option<&SandboxPolicy>, sandbox: &str, args: &[String], exit_code: i32, duration_ms: u64)` 等——按 `policy.audit.exec` 门控,发射结构化 tracing 事件
- 拒绝与资源类似 helper
- 单测:audit.exec=false 不发射;true 发射正确字段

### T2 — exec 审计接线
- `commands/mod.rs` run_exec(blocking)与 `sandbox.rs` sandbox_exec:exec 完成(或失败)时,若 policy.audit.exec → 记录(含 exit_code、耗时)
- background exec(sessions.rs):完成时记录(audit.exec)
- 测试:engine 测试断言 audit 事件字段

### T3 — 拒绝审计接线
- sandbox_exec 失败且错误含 "denied"(sandlock 拒绝)时,policy.audit.deny → 记录
- 测试:mock 返回 denied 错误 → audit.deny 事件

### T4 — 资源审计(轻量)
- sandbox_create 的 limits 记录、resize 操作 → policy.audit.resource 门控记录
- 注:VM 级资源(cpus/mem)已有 `info` 命令;sandbox 级资源度量(guest 内)留待未来(依赖 guest 侧)——本阶段记录"资源声明与调整"审计

### T5 — 文档
- docs/protocol.md:sandbox_exec 的 audit 语义说明
- docs/design/policy-model.md:AuditSpec 接线状态更新

## 3. 明确不做

- 独立审计协议/存储(审计事件 = tracing 输出,消费方负责聚合)
- guest 内进程级资源度量(sandbox 实际 CPU/内存)——需 guest 侧采集,留待未来
- 审计事件协议化(不进 JSON 协议——降低协议面,日志即接口)

## 4. 验证

- 全门禁 + 引擎 audit 测试
- 真实 e2e:带 audit 策略的 sandbox,执行后 daemon 日志出现结构化 audit 事件
